# Backend audit and remediation plan

Этот документ — рабочий чеклист аудита бэкенда Fuze. Пункты расположены сверху вниз по влиянию: сначала уязвимости, потеря контроля доступа и полностью сломанные сценарии, затем ошибки данных и архитектуры, в конце — качество, удобство разработки и косметические замечания.

> Статус на 2026-08-07. Аудит выполнен без изменения кода. Модуль плейлистов находится в незавершённом и частично незакоммиченном состоянии.

## Правила работы с планом

- [x] Исправлять блоки по порядку приоритета: P0 → P1 → P2 → P3.
- [x] Для каждого исправления сначала добавить тест, воспроизводящий ошибку.
- [x] Не считать пункт завершённым без проверки негативного сценария.
- [x] Для изменений схемы БД всегда добавлять и проверять Alembic-миграцию.
- [x] Не смешивать крупный рефакторинг и новый пользовательский функционал в одной задаче.

## P0 — критические проблемы безопасности и неработающие сценарии

Эти пункты блокируют безопасное развитие проекта. Они позволяют обходить ограничения доступа, оставляют действующий доступ заблокированным пользователям либо приводят к гарантированным 500 в основных сценариях.

### Авторизация использует роль из устаревшего JWT

Файл: `src/backend/modules/users/dependencies.py:11`

`require_role` доверяет роли из access token и не загружает актуального пользователя из БД. После смены роли или удаления пользователя старый токен продолжает предоставлять прежние права до истечения срока.

- [ ] Сделать единую dependency получения текущего пользователя.
- [ ] Валидировать токен и безопасно разбирать `sub`.
- [ ] Загружать пользователя из БД.
- [ ] Возвращать 401, если пользователь удалён или не найден.
- [ ] Проверять актуальную роль из БД, а не только claim JWT.
- [ ] Добавить тест: роль ADMIN понижена до USER, старый токен больше не даёт admin-доступ.
- [ ] Добавить тест: удалённый пользователь со старым токеном не имеет доступа.

### Не проверяется `is_active`

Файлы:

- `src/backend/modules/auth/service.py:27`
- `src/backend/modules/auth/router.py:22`
- `src/backend/modules/auth/router.py:32`
- `src/backend/modules/users/dependencies.py:11`

Неактивный пользователь может войти, обновить токены, вызвать `/auth/me` и использовать защищённые endpoints.

- [ ] Запретить login для неактивного пользователя.
- [ ] Проверять `is_active` в общей dependency текущего пользователя.
- [ ] Повторно проверять активность при refresh.
- [ ] Определить единый статус ответа: 401 или 403.
- [ ] При неуспешном refresh очищать auth cookies.
- [ ] Добавить тесты login/me/refresh/access для неактивного пользователя.

### `require_role(USER)` не разрешает доступ администратору

Файлы:

- `src/backend/modules/users/dependencies.py:11`
- `src/backend/modules/tracks/router.py:14`

Роли сравниваются как независимые значения. Поэтому ADMIN не получает доступ к пользовательским endpoints треков.

- [ ] Зафиксировать модель ролей: `ADMIN >= USER`.
- [ ] Реализовать иерархию централизованно в одной dependency.
- [ ] Не дублировать `USER or ADMIN` в каждом router.
- [ ] Добавить параметризованные тесты матрицы доступа USER/ADMIN.
- [ ] Оставить возможность перейти к permissions/capabilities при появлении новых ролей.

### Cookie-аутентификация работает без CSRF-защиты

Файл: `src/backend/core/security.py:19`

JWT принимаются из cookies, но `JWT_COOKIE_CSRF_PROTECT=False`. Изменяющие состояние запросы могут быть уязвимы к CSRF.

- [ ] Выбрать единую модель: защищённые HttpOnly cookies или Bearer access token.
- [ ] Если остаются cookies — включить и протестировать CSRF-защиту.
- [ ] Явно настроить `Secure`, `HttpOnly`, `SameSite`, domain и path cookies.
- [ ] Проверить CORS вместе с `allow_credentials`.
- [ ] Добавить тест запроса без CSRF-токена.
- [ ] Добавить тест запроса с неверным CSRF-токеном.

### GET плейлиста всегда падает

Файл: `src/backend/modules/playlists/service.py:16`

ORM-объект `Playlist` распаковывается через `**playlist`, хотя он не является mapping. Успешный GET завершается `TypeError` и ответом 500.

- [ ] Перестать распаковывать ORM-объект через `**`.
- [ ] Явно формировать DTO/response schema.
- [ ] Добавить тест успешного получения плейлиста.
- [ ] Добавить тест корректного `tracks_count`.

### Создание плейлиста сохраняет данные, но может вернуть 500

Файлы:

- `src/backend/modules/playlists/router.py:20`
- `src/backend/modules/playlists/schemas.py:12`

POST возвращает ORM-модель без обязательного `tracks_count`. Плейлист коммитится, затем FastAPI может выбросить `ResponseValidationError`. Клиент видит ошибку и может повторно создать сущность.

- [ ] Формировать полный ответ, включая `tracks_count=0`.
- [ ] Проверить response schema через тест endpoint.
- [ ] Исключить состояние «операция выполнена, но клиент получил 500».
- [ ] Рассмотреть статус 201 для создания.

### В production отсутствуют таблицы плейлистов

Каталог: `src/backend/alembic/versions/`

Модели `Playlist` и `PlaylistTrack` есть, но миграции для них нет. `alembic upgrade head` не создаёт соответствующие таблицы.

- [ ] Сначала завершить проектирование модели плейлистов.
- [ ] Создать Alembic-миграцию для обеих таблиц.
- [ ] Проверить primary keys, foreign keys, индексы и unique constraints.
- [ ] Прогнать upgrade на чистой БД.
- [ ] Прогнать downgrade и повторный upgrade.
- [ ] Добавить автоматическую проверку миграций в тестах/CI.

### Плейлисты не имеют владельца и публично доступны

Файлы:

- `src/backend/modules/playlists/models.py:7`
- `src/backend/modules/playlists/router.py:8`

У `Playlist` нет `owner_id`, а router не требует аутентификации. Любой клиент может создавать и читать плейлисты.

- [ ] Определить типы плейлистов: личный, публичный, системный.
- [ ] Добавить владельца плейлиста.
- [ ] Запретить изменение чужого плейлиста обычному пользователю.
- [ ] Разрешить администратору доступ согласно выбранной политике.
- [ ] Определить правила чтения публичных и приватных плейлистов.
- [ ] Добавить тесты owner / other user / admin / anonymous.

## P1 — серьёзные логические ошибки и целостность данных

Эти проблемы могут приводить к неверным данным, повторным операциям, неожиданным 500 и неправильному аудио.

### Refresh удалённого пользователя даёт 500

Файл: `src/backend/modules/auth/router.py:39`

Результат поиска пользователя используется без проверки. Для удалённого пользователя обращение к `user.id`/`user.role` вызывает `AttributeError`.

- [ ] Обрабатывать отсутствие пользователя до генерации токенов.
- [ ] Возвращать корректную auth-ошибку вместо 500.
- [ ] Очищать cookies при отклонённом refresh.
- [ ] Добавить тест refresh после удаления пользователя.

### `/auth/me` удалённого пользователя может дать 500

Файл: `src/backend/modules/auth/router.py:22`

Endpoint может вернуть `None` при обязательной response model.

- [x] Перевести endpoint на общую dependency текущего активного пользователя.
- [ ] Добавить тест `/auth/me` после удаления пользователя.

### Refresh-токены нельзя отозвать

Logout удаляет cookies только в текущем браузере. Скопированный refresh token остаётся действительным; старый refresh token продолжает работать после rotation.

- [ ] Как минимум проверять пользователя и `is_active` при refresh.
- [ ] Определить модель серверной сессии или token version.
- [ ] Добавить `jti`/идентификатор сессии при необходимости отзыва отдельных устройств.
- [ ] Реализовать rotation refresh token с инвалидированием предыдущего.
- [ ] Определить logout одного устройства и logout всех устройств.
- [ ] Добавить тест повторного использования старого refresh token.

### Токены одновременно возвращаются в JSON и cookies

Файл: `src/backend/modules/auth/router.py:46`

Это создаёт две параллельные модели хранения и повышает риск утечки refresh token через frontend, логи или XSS.

- [ ] Выбрать единый контракт хранения токенов.
- [ ] Не отдавать refresh token JavaScript-коду без необходимости.
- [ ] Обновить документацию и frontend под выбранный контракт.

### Позиция следующего трека вычисляется в обратную сторону

Файл: `src/backend/modules/playlists/repository.py:31`

Используется `max(position) - 1`. Позиции будут равны `1, 0, -1...`.

- [ ] Выбрать начало индексации: 0 или 1.
- [ ] Исправить направление расчёта на добавление следующей позиции.
- [ ] Добавить тест последовательного добавления нескольких треков.

### Позиции треков не защищены от дублей и гонок

В таблице нет уникальности `(playlist_id, position)`. Параллельные добавления могут получить одинаковую позицию.

- [ ] Добавить unique constraint для `(playlist_id, position)`.
- [ ] Всегда сортировать треки по позиции при чтении.
- [ ] Определить транзакционную стратегию добавления и перемещения.
- [ ] Добавить тест конкурентного или повторного добавления.

### Не определено каскадное удаление связей плейлиста

Файл: `src/backend/modules/playlists/models.py:14`

У relationships и foreign keys нет осознанных `cascade`/`ondelete`. Удаление Playlist или Track может завершиться ошибкой FK или потребовать ручной очистки.

- [ ] Определить поведение при удалении плейлиста.
- [ ] Определить поведение при удалении трека.
- [ ] Настроить ORM cascade и DB `ondelete` согласованно.
- [ ] Добавить тесты удаления связанных сущностей.

### Один и тот же трек нельзя добавить в плейлист повторно

Файл: `src/backend/modules/playlists/models.py:20`

Составной primary key `(playlist_id, track_id)` запрещает повтор трека. Это может быть правильным ограничением, но сейчас оно не зафиксировано как продуктовая политика.

- [ ] Решить, допустимы ли повторы треков.
- [ ] Если допустимы — дать `PlaylistTrack` собственный id.
- [ ] Если не допустимы — возвращать понятный 409, а не DB exception.
- [ ] Закрепить решение тестом.

### Отсутствующий плейлист даёт 500 вместо 404

Файл: `src/backend/modules/playlists/service.py:14`

`None` используется как существующая сущность.

- [ ] Добавить доменную ошибку `PlaylistNotFound`.
- [ ] Отображать её в 404.
- [ ] Добавить тест отсутствующего id.

### API плейлистов не завершён

Repository содержит добавление и удаление треков, но service/router их не предоставляют. Нет list/update/delete плейлистов.

- [ ] Добавить список доступных пользователю плейлистов.
- [ ] Добавить update/delete плейлиста.
- [ ] Добавить add/remove/reorder track.
- [ ] Проверять существование Playlist и Track до изменения связи.

### Поиск треков записывает все результаты в БД

Файл: `src/backend/modules/tracks/service.py:20`

Обычный поиск создаёт до десяти Track. База растёт от поисковых запросов, а поисковые боты могут заполнить таблицу мусором.

- [ ] Отделить внешний search result от сохранённой сущности Track.
- [ ] Сохранять Track при явном выборе, добавлении или скачивании.
- [ ] Либо реализовать контролируемый batch upsert и политику очистки.
- [ ] Добавить тест, что простой поиск не создаёт нежелательные записи.

### Один поиск выполняет до десяти отдельных commit

Файлы:

- `src/backend/modules/tracks/service.py:20`
- `src/backend/modules/tracks/repository.py:35`

Запрос может частично записать результаты и упасть посередине.

- [ ] Перенести границу транзакции на уровень use case/service.
- [ ] Использовать одну транзакцию или batch operation.
- [ ] Добавить rollback при ошибке.

### Параллельные поиски могут завершаться 500

Два запроса одновременно не находят Track, затем оба вставляют одинаковые `(source, source_id)`. Один получает `IntegrityError`.

- [ ] Использовать PostgreSQL upsert либо обработать unique conflict.
- [ ] После конфликта делать rollback и повторное чтение.
- [ ] Добавить тест или отдельную интеграционную проверку гонки.

### Первый результат YouTube считается правильным треком

Файл: `src/backend/modules/tracks/service.py:66`

Первым результатом может быть remix, live, cover, клип или другая композиция.

- [ ] Нормализовать artist/title.
- [ ] Сравнивать длительность Yandex и YouTube.
- [ ] Ввести допустимое расхождение duration.
- [ ] Отбрасывать очевидные remix/live/cover при отсутствии таких маркеров в исходнике.
- [ ] В неоднозначном случае разрешить выбор пользователю.
- [ ] Сохранять источник и качество сопоставления.

### Скачивание выполняется внутри HTTP-запроса

Файл: `src/backend/modules/tracks/service.py:49`

Поиск, загрузка, перекодирование и upload занимают весь жизненный цикл запроса. Возможны timeout, повторные запросы и занятые workers.

- [ ] Описать состояния job: pending/running/ready/failed.
- [ ] Вынести тяжёлую работу в отдельный worker/очередь.
- [ ] Возвращать job id или состояние трека сразу.
- [ ] Добавить endpoint проверки состояния.
- [ ] Продумать retry, timeout и сохранение причины ошибки.

### Параллельные download одного трека не координируются

Несколько запросов одновременно увидят пустой `storage_key` и начнут одинаковую загрузку.

- [ ] Добавить атомарный переход состояния загрузки.
- [ ] Либо использовать distributed lock с ограниченным временем жизни.
- [ ] Сделать повторный запрос идемпотентным.
- [ ] Добавить проверку конкурентного запуска.

### Ошибки внешних сервисов имеют неправильные HTTP-статусы

Файл: `src/backend/modules/tracks/router.py:34`

Любой `ValueError` превращается в 404.

- [ ] Разделить доменные ошибки: TrackNotFound, MatchNotFound, ProviderUnavailable, DownloadFailed, StorageUnavailable.
- [ ] Использовать 404 только для отсутствующей сущности.
- [ ] Использовать 422/409 для невозможности сопоставить трек.
- [ ] Использовать 502/503 для недоступного внешнего провайдера.
- [ ] Добавить тест отображения каждой ошибки в HTTP.

### После неудачной загрузки остаётся частично обновлённый Track

Файл: `src/backend/modules/tracks/service.py:69`

`yt_url` коммитится до скачивания и upload, но состояние процесса не хранится.

- [ ] Добавить явный статус загрузки.
- [ ] Хранить время попытки и безопасное описание последней ошибки.
- [ ] Определить, какие промежуточные поля сохраняются при failed.
- [ ] Сделать retry предсказуемым.

### Duplicate email при гонке превращается в 500

Файлы:

SELECT перед INSERT не защищает от параллельной регистрации.

### PATCH принимает произвольную роль

### Email не нормализуется

- [ ] Добавить тест разных регистров.

## P2 — архитектурный долг, мешающий новому функционалу

Эти пункты не обязательно ломают приложение прямо сейчас, но заметно увеличат стоимость и риск следующих функций.

### Транзакции управляются репозиториями

Файлы:

- `src/backend/modules/users/repository.py`
- `src/backend/modules/tracks/repository.py`
- `src/backend/modules/playlists/repository.py`

Каждый create/update/delete самостоятельно делает commit. Сервис не может объединить несколько действий атомарно.

- [ ] Определить границу транзакции на уровне use case/service.
- [ ] Оставить repository операции query/add/flush без самостоятельного commit.
- [ ] Добавить централизованный commit/rollback.
- [ ] Рассмотреть Unit of Work, когда появятся составные операции.
- [ ] Перепроверить все сценарии частичного сохранения.

### Слои возвращают несовместимые типы

UsersService возвращает ORM, TracksService — `dict`, PlaylistsService смешивает ORM и `dict`.

- [ ] Зафиксировать границы слоёв.
- [ ] Repository должен работать с ORM.
- [ ] Service должен возвращать доменный объект или DTO.
- [ ] Router должен работать с Pydantic request/response schemas.
- [ ] Не передавать наружу поля ORM случайно.

### Динамический загрузчик модулей скрывает внутренние ошибки импортов

Файл: `src/backend/core/modules.py:32`

Любой `ModuleNotFoundError` внутри модуля трактуется как отсутствие metadata/router. Ошибка зависимости может молча выключить целый модуль.

- [ ] Подавлять исключение только при отсутствии ожидаемого optional-файла.
- [ ] Пробрасывать ошибки внутренних импортов.
- [ ] Логировать traceback при ошибке загрузки.
- [ ] Добавить тест модуля с ошибочным внутренним импортом.

### Нет формализованной модели ошибок

Часть кода использует `AppException`, часть — `HTTPException`, часть — `ValueError`, остальные ошибки превращаются в общий 500.

- [ ] Определить доменные исключения по модулям.
- [ ] Не использовать `ValueError` для бизнес-ошибок.
- [ ] Централизованно переводить доменные ошибки в HTTP.
- [ ] Не привязывать service к HTTP-статусам.
- [ ] Добавить безопасное логирование context/correlation id.

### PATCH молча игнорирует явно переданный `null`

Файл: `src/backend/modules/users/service.py:54`

Сейчас не различаются понятным образом «поле не передано» и «поле передано как null».

- [ ] Определить семантику для каждого nullable поля.
- [ ] Если очистка запрещена — отклонять null схемой.
- [ ] Если разрешена — отличать null от unset.

## P3 — тесты, инфраструктура и небольшие помехи

## Definition of Done для нового функционала

Перед добавлением новой backend-функции проверить:

- [ ] Определено, кто имеет доступ: anonymous / user / owner / admin.
- [ ] Проверяется текущий активный пользователь из БД.
- [ ] Есть request и response schemas с ограничениями.
- [ ] Определены 404, 409, 422 и ошибки внешних сервисов.
- [ ] Составная операция атомарна или имеет явную state machine.
- [ ] Обработаны повторный запрос и конкурентный запуск.
- [ ] Для изменения БД есть Alembic-миграция.
- [ ] Есть позитивный тест.
- [ ] Есть тест отсутствующей сущности.
- [ ] Есть тест недостаточных прав.
- [ ] Есть тест некорректных входных данных.
- [x] Ruff и весь набор тестов проходят из корня проекта.
